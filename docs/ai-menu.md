# AI menu generation

The weekly-plan screen has a **Create menu with AI** button. A modal collects the target week, 1–12 diners, days (Monday–Sunday), meal times (breakfast/lunch/dinner), cuisines, cooking appliances, dietary restrictions, available ingredients, cooking-time limit, budget preference and a custom request. The number of slots is derived from selected days × meal times (1–21). The family master prompt is editable and shared in Cloudflare D1.

The user reviews the complete request before **Generate menu** starts the server workflow. The current plan remains unchanged while generating and editing the draft. The draft can be reopened on another device with the family code. Edited meals are saved with conditional revision checks. **Apply this menu** archives the prior week, preserves physical prepared-food records, resets plan-specific progress and switches to the selected week. An active timer, cooking batch, storage recovery or unresolved cross-tab conflict prevents replacement. Changes received while the modal was open require reviewing again before applying. When Family Sync is connected, the accepted state follows its existing conditional-save flow; otherwise it remains on the device until the user connects Family Sync.

## Appliances

Options include air fryer, electric/induction/gas stove, blender, oven, microwave, rice cooker, steamer and pressure cooker, plus a custom appliance. Users must select at least one option. **No heating appliance** requests cold meals and cannot be combined with another appliance. Basic knives, boards, bowls and cookware are assumed. Requirements include the selected appliances; every generated meal declares its required appliances. The server rejects unselected declarations and detects common unselected appliance names in instructions. This catches common mistakes but cannot prove that arbitrary natural-language instructions require no other equipment. Review the draft before cooking.

## Provider and cost controls

- Uses the stateless [Gemini Interactions API](https://ai.google.dev/gemini-api/docs/interactions) (`store: false`), with fixed server-side model `gemini-3.5-flash-lite`, constrained JSON output with server validation, one request per selected meal time plus one request for five alternatives (2–4 primary calls per menu), each covering at most seven days with a 180-second deadline and 32,768-token ceiling. Google documents [3.5 Flash-Lite as a stable model](https://ai.google.dev/gemini-api/docs/models/gemini-3.5-flash-lite) with a 65,536-token output limit and a [free API tier](https://ai.google.dev/gemini-api/docs/pricing#gemini-3.5-flash-lite). Production checks found repeated HTTP 503 overloads on the previous 3.1 Flash-Lite model; this switches the single configured model rather than adding retries or paid fallback. No personal ChatGPT account, model chosen by a browser request or automatic regeneration is used.
- The site owner supplies **GEMINI_API_KEY** privately in Cloudflare Worker Settings → Variables and Secrets. Keep the key out of `VITE_*` variables and source control. For a free-only deployment, use a Google AI Studio project without paid billing enabled and verify the model's current free-tier availability for the project/region. Code cannot determine the billing tier of an API key; a model being eligible for a free tier does not make requests free on a billed project. See https://ai.google.dev/gemini-api/docs/pricing .
- Default family-wide limit: 10 completed or admitted in-progress menus per UTC day. **AI_MAX_DAILY_REQUESTS** may be set by the site owner from 0 to a hard maximum of 10. A single conditional D1 update enforces admission across instances using durable job status. Failed and rejected attempts do not consume an allowance. Existing successful menus still count; historical attempt counters are retained but no longer block generation. The UI shows remaining slots and the reset time in the device's timezone (midnight UTC is 07:00 in Vietnam). Provider quotas remain separate; the app does not automatically regenerate failed jobs.
- Duplicate submission IDs and repeated background invocations do not generate again. Opening a saved menu, editing a draft and switching languages make no additional Gemini calls.
- Generated English recipe text has an exact-source Vietnamese translation map stored with the plan. Quantities and instruction tokens must remain unchanged. Unknown manually edited text no longer matches its prior translation; ordinary app translation fallback may then apply.
- Gemini returns each visible field as an English/Vietnamese pair. The server builds the saved translation map from those pairs, avoiding a separate source-text list that can omit or mismatch recipe fields. English and Vietnamese are produced together in each meal-time request, avoiding separate translation calls or a second copy of every English instruction in the response.
- Each request includes one complete representative recipe from `public/meal-plan.json`, paired with its bundled Vietnamese translations, its original serving count and a compact vocabulary of default ingredient names. Gemini uses this example for detail and naming consistency while the current form controls ingredients, cuisine, servings, restrictions and equipment. A single recipe example keeps input quota lower than sending the entire default week.
- Form data and the master prompt are sent to Gemini, or Cloudflare AI when the backup is used. Free-tier data handling differs from paid services; review Google's current terms and avoid unnecessary personal information. The UI shows a short disclosure before generation. AI suggestions are not allergy or food-safety certification; the server also checks known restricted ingredients using the app's existing ingredient-warning rules.

Cloudflare Workers, D1 and Workflows have their own free-tier limits, separately from Gemini's quota. The deployment scripts do not enable a paid plan.

## Cloudflare AI backup

The Worker has an `AI` binding and uses `@cf/qwen/qwen3-30b-a3b-fp8` only when a Gemini batch fails (including quota, availability, network, credentials or invalid output), or the Gemini key is absent. It makes one backup attempt per batch, with the same requirements, reference recipe, selected equipment, restrictions and strict recipe validation. For alternatives, a small planning request first chooses five distinct bilingual names; a keyed recipe schema fixes each name to its own complete recipe. Appliance declarations, units and cooking-time estimates are constrained in the Cloudflare decoder as well as checked by the server. A successful Gemini batch never calls the backup. Durable Workflow results retain which providers were used. Before generation, the UI shows configured primary and backup providers. During generation it polls a separate progress document for the active provider, current meal batch and fallback reason. After generation it names every provider used, including Gemini-only menus. Progress writes do not change the job revision used for conditional final-result saves. Legacy drafts without provider metadata are explicitly labelled as unrecorded. A complete menu is saved only after all scheduled batches and the alternatives succeed. Quantity notation is normalized without changing numeric values (for example, Vietnamese decimal commas, unit names and bracket spacing). If bilingual fields still omit or change protected quantities/numbers, one bounded translation-only request repairs at most 24 fields. Every number, time, temperature and ingredient token is masked with an immutable marker; missing, duplicated, reordered or invented markers/numbers are rejected before restoring the exact source values. English recipes and all final recipe/restriction checks remain unchanged. The repair request uses at most 12,000 input bytes and 4,096 output tokens, and consumes a backup-call allowance. There is no full-menu retry loop. The UI displays planning and translation-repair activity.

[Workers AI includes 10,000 neurons per UTC day](https://developers.cloudflare.com/workers-ai/platform/pricing/). This model supports the free plan. The app independently caps regular backup calls at six per UTC day and bounds each input to 64,000 bytes and each output to 16,384 tokens. Administrative checks have a separate eight-call cap, smaller 24,000-byte inputs and the same output ceiling, keeping their worst-case combined budget below 10,000 neurons without consuming the family's six-call allowance. Other Workers AI usage on the same account shares the account allowance. The code does not enable paid billing; an already billed Cloudflare account follows Cloudflare's own pricing. Exhausted quota or invalid backup output leaves the current plan intact.

## Five alternatives and meal replacement

Both plan schemas accept an optional `alternatives` array with at most five complete recipes. Alternative recipes have unique IDs, ingredients, preparation, cooking, storage and optional equipment, but no `day` or `type`. They do not contribute to meal count, shopping, preparation or food consumption until chosen. Generated menus contain exactly five distinct alternatives, with the full week's constraints and scheduled dishes supplied as context. The bundled default includes five bilingual alternatives; an unchanged older default plan gains them during hydration. Custom or restricted older plans are preserved without injecting default dishes.

**Replace meal** opens an accessible dialog on an AI preview card or active weekly card. Users compare time, equipment and expandable ingredients/instructions, choose one recipe and confirm. Only that slot changes; the displaced recipe takes the selected option's place so five choices remain and the change can be reversed. Ingredient links are rebased, stale scheduled container labels are removed from recipes returned to the pool, shopping/preparation progress is recomputed, and physical food and other slots are retained. Eaten meals and meals with active cooking/timers cannot be swapped. Active-plan changes support the existing Undo action. Draft swaps use the existing revision-checked save before applying. Cancelling, comparing and swapping make no AI requests.

## Remembered family connection

After a successful family or AI-settings connection, the verified family code is stored in this browser's local storage, outside planner exports. Family Sync stores a small revision/fingerprint checkpoint and automatically resumes after reload. Pending local changes use the saved revision for a conditional write; conflicts pause sync and preserve the device copy. The Access sign-in requirement still applies. **Disconnect** removes the remembered code and sync checkpoint. An AI-only remembered code can also be removed with **Forget code in this browser**. Clearing browser data removes it; another device needs its own initial connection. If browser storage is unavailable, the current tab remains usable without persistence.

## Runtime and authentication

`/api/ai-menu` requires Access sign-in and the existing family code, validates inputs, saves master-prompt preferences/drafts and starts a Cloudflare Workflow. `MenuWorkflow` claims the job once, generates each selected meal time in its own durable step, validates each batch and assembles the complete plan before saving a ready draft. A failed batch stops the job; no partial plan is published and no remaining batch is called. Successful step results can be replayed without repeating their provider call. Neither writes the active family planner. Queued/running jobs older than 20 minutes are reported as timed out.

The server-only D1 `ai` namespace contains settings, jobs and per-day allowance records. All application routes to it require the family code. Data is not saved into the Git repository. Provider error messages and API keys are not returned to the browser. Failed jobs may retain a numeric HTTP status, an allowlisted provider status and a fixed provider/validation diagnostic category. Instruction-detail failures can also record the canonical slot ID and numeric step/character counts; diagnostics exclude recipe text, prompts and credentials.

An administrator may seed a synthetic job with the internal diagnostic flag to capture a key-redacted provider message in the separate D1 `diagnostics` namespace. The generation API ignores that flag in browser requests. Remove the diagnostic record after troubleshooting; ordinary family jobs do not capture provider text.

The Interactions response format supplies a compact JSON schema with required fields and one outer bound for the exact number of meals. Nested numeric bounds, array-length bounds and enums are removed from the decoder schema because combining those constraints across recipe lists exceeded Google's serving-state limit in live checks. The full constraints and requested slot order remain in the prompt and are enforced by server validation. Only completed model-output text is read; thought steps and incomplete results are not accepted as recipes. One reusable recipe shape is used in an ordered array, avoiding a separate schema property for every slot. A 21-item bound still exceeded serving limits in live checks; splitting by meal time keeps each constrained array at seven or fewer recipes. Later batches receive the full-week requirements and compact summaries of meals already planned in this week, including main/side dishes and ingredient names, quantities and units. This lets the model distinguish fish species and coordinate protein rotation across breakfast, lunch and dinner. Previous-menu dishes stay in a separate avoidance list. A full week uses at most three provider calls, generated sequentially; opening, editing and translating a saved plan add no calls. Required English/Vietnamese pairs constrain missing-language errors; the server assigns canonical IDs, days and meal types from the ordered request slots. Earlier keyed bilingual results remain compatible. A previous schema with a required object property for every slot exceeded decoder constraints; plain JSON mode also allowed occasional missing bilingual fields. Validation enforces the exact requested meal count and slots, at most 30 ingredients, 10 preparation steps and 15 cooking steps per meal, complete bilingual text and quantity preservation. Invalid output never becomes an active or ready plan.

The translation map uses a protected dictionary during validation, then becomes a plain object through object spread before the Workflow step returns. Cloudflare's durable step serializer rejects null-prototype dictionaries. Object spread keeps keys such as `__proto__` as ordinary own properties without invoking a prototype setter.

Generated recipes also have a basic completeness floor: a separate side needs ingredient coverage, common bread/rice sides must appear in the ingredient list, and heated recipes need at least three actionable steps with 120 characters of cooking guidance. Ingredient amounts appearing in instructions must use scalable bracket tokens. Legitimate simple cold dishes with no side remain supported. These checks do not certify culinary completeness, allergy safety or nutritional adequacy; the draft remains editable and requires review.

Cloudflare Access email OTP replaces Netlify SSO on the new hostname. Only the configured owner email may sign in. The Worker verifies the Access JWT, and private planner/AI routes also require the family code. Workflows start through a server binding without forwarding login cookies. If the session expires, the sign-in link opens a new tab so the original form remains available. Legacy Netlify Functions remain for rollback only.

## Data compatibility

Schema v1 retains exactly ten weekday lunch/dinner slots. Schema v2 accepts 1–21 unique slots across all seven days and all three meal types, plus optional appliance metadata, up to five unscheduled `alternatives`, and an exact-source Vietnamese translation map. Legacy defaults and backups remain v1 and continue to work. The calendar, cooking picker, saved-food schedules, backup validation, shopping and preparation accept v2. Missing preparation compatibility profiles remain individual tasks rather than guessing shared preparation.

## Default preferences

The [English default master prompt](default-master-prompt.md) prefers Central Vietnamese home cooking, normally uses each savory main once (at most twice when necessary), varies actual primary ingredients and fish species rather than only cooking methods, rotates protein groups, includes occasional simple meals and shares vegetables/seasonings for shopping and preparation. Every Vietnamese field must use natural Vietnamese with full diacritics; corresponding English fields support the English interface. Form restrictions take precedence.

These are generation instructions, not a deterministic semantic validator for dish identity or fish species. Review the generated draft before applying. Starting a new request uses the current shared prompt instead of inheriting an older draft's instructions. **Use default prompt** restores the current English default in the form; **Save master prompt** persists it if the family wants to replace a custom setting. Existing settings continue to use their saved prompt.

The default-preference update passed 33 focused frontend/server tests, 16 Cloudflare tests, frontend/Worker TypeScript checks and the production build. Four Chromium cases checked current-default loading after an older saved draft, restoring the English default, saving shared settings and dialog layout in English/Vietnamese at mobile and laptop sizes. Those checks use local endpoints and make no live Gemini calls.

## Additional-request precedence and checks

The complete request is sent verbatim at high priority. Hard form limits and the bilingual schema take precedence; explicit request details then override default/master cuisine and variety preferences. Clear English/Vietnamese meal counts, cuisine, common required/excluded foods, cooking methods and a named day/meal are compiled locally into weekly slot requirements without another AI call. For example, “I need 1 western meal with fried fish and broccoli” reserves one scheduled slot for a Western fried-fish meal containing actual fish and broccoli. A named Monday dinner stays Monday dinner across separate lunch/dinner batches. When no slot is named, the earliest available selected slot is shown in the request preview. Unrecognized or ambiguous preferences stay in the verbatim instructions rather than being presented as verified rules.

Checks use real ingredient lists, cuisine metadata and cooking instructions, not just dish titles. Fish sauce does not satisfy a required fish ingredient, other greens do not satisfy broccoli, and frying a side alongside steamed fish does not satisfy fried fish. Exact weekly cuisine counts are checked across batches and again on the assembled menu. An incompatible requested slot/diet/exclusion is reported before spending a generation. A Gemini result that violates recognized requirements can fall back to Cloudflare; invalid results are never promoted to a ready draft. The five unscheduled alternatives obey global exclusions/preferences, while dated/count-specific clauses remain attached to scheduled slots. Cuisine authenticity and all other natural-language preferences still require recipe review.

## Prep Day recipe cards

Generated and edited preparation tasks without reviewed compatibility profiles are presented in one card per scheduled meal, with its day, meal time and preparation-step count. The underlying task groups and completion keys remain unchanged: individual instructions, ingredient allocations, storage, checkboxes and undo are retained. Reviewed compatible ingredient batches remain grouped by ingredient/operation. This removes repeated recipe-title cards without treating different instructions as duplicates or merging preparation across unrelated meals.

Generation feedback includes an immediate submission spinner, live meal-time/alternative batch progress, a validation stage, and distinct success/failure panels. Failed drafts offer **Retry generation** with the same household answers and master prompt, or **Edit request**. A terminal failure gets a new job ID; a retry after an uncertain network response keeps its original ID to avoid duplicate jobs. Applying a ready draft remains a separate action.

Cloudflare recipe schemas bound ingredient lists, preparation/cooking step counts, and bilingual text lengths. The schema is sent through `response_format` once rather than duplicated in the user prompt. Truncated provider responses are rejected with `output_limit` and an explicit retry message; incomplete JSON is never applied or padded with invented recipe data. Family allowance and provider free-tier caps continue to apply.

Scheduled custom requests are scoped before sending each batch: parsed requests assigned to another meal time are removed from that batch's prose and represented as reserved combinations. Unparsed preferences and global exclusions remain available, and validation still checks the original full-week request. This prevents a Monday dinner request from being repeated in Monday lunch.
