# AI menu generation

The weekly-plan screen has a **Create menu with AI** button. A modal collects the target week, 1–12 diners, days (Monday–Sunday), meal times (breakfast/lunch/dinner), cuisines, cooking appliances, dietary restrictions, available ingredients, cooking-time limit, budget preference and a custom request. The number of slots is derived from selected days × meal times (1–21). The family master prompt is editable and shared in Cloudflare D1.

The user reviews the complete request before **Generate menu** calls Gemini. The current plan remains unchanged while generating and editing the draft. The draft can be reopened on another device with the family code. Edited meals are saved with conditional revision checks. **Apply this menu** archives the prior week, preserves physical prepared-food records, resets plan-specific progress and switches to the selected week. An active timer, cooking batch, storage recovery or unresolved cross-tab conflict prevents replacement. Changes received while the modal was open require reviewing again before applying. When Family Sync is connected, the accepted state follows its existing conditional-save flow; otherwise it remains on the device until the user connects Family Sync.

## Appliances

Options include air fryer, electric/induction/gas stove, blender, oven, microwave, rice cooker, steamer and pressure cooker, plus a custom appliance. Users must select at least one option. **No heating appliance** requests cold meals and cannot be combined with another appliance. Basic knives, boards, bowls and cookware are assumed. Requirements include the selected appliances; every generated meal declares its required appliances. The server rejects unselected declarations and detects common unselected appliance names in instructions. This catches common mistakes but cannot prove that arbitrary natural-language instructions require no other equipment. Review the draft before cooking.

## Provider and cost controls

- Uses the stateless [Gemini Interactions API](https://ai.google.dev/gemini-api/docs/interactions) (`store: false`), with fixed server-side model `gemini-3.5-flash-lite`, constrained JSON output with server validation, a 180-second deadline/32,768-token ceiling for up to 10 meals, or 360 seconds/65,536 tokens for larger weeks. Google documents [3.5 Flash-Lite as a stable model](https://ai.google.dev/gemini-api/docs/models/gemini-3.5-flash-lite) with a 65,536-token output limit and a [free API tier](https://ai.google.dev/gemini-api/docs/pricing#gemini-3.5-flash-lite). Production checks found repeated HTTP 503 overloads on the previous 3.1 Flash-Lite model; this switches the single configured model rather than adding retries or paid fallback. No personal ChatGPT account, model chosen by a browser request, paid-provider fallback or automatic regeneration is used.
- The site owner supplies **GEMINI_API_KEY** privately in Cloudflare Worker Settings → Variables and Secrets. Keep the key out of `VITE_*` variables and source control. For a free-only deployment, use a Google AI Studio project without paid billing enabled and verify the model's current free-tier availability for the project/region. Code cannot determine the billing tier of an API key; a model being eligible for a free tier does not make requests free on a billed project. See https://ai.google.dev/gemini-api/docs/pricing .
- Default family-wide limit: 3 submitted jobs per UTC day. **AI_MAX_DAILY_REQUESTS** may be set by the site owner from 0 to a hard maximum of 10. D1 compare-and-set operations enforce the counter across instances. Attempts that fail after submission consume one allowance; there is no automatic retry spending another allowance.
- Duplicate submission IDs and repeated background invocations do not generate again. Opening a saved menu, editing a draft and switching languages make no additional Gemini calls.
- Generated English recipe text has an exact-source Vietnamese translation map stored with the plan. Quantities and instruction tokens must remain unchanged. Unknown manually edited text no longer matches its prior translation; ordinary app translation fallback may then apply.
- Gemini returns each visible field as an English/Vietnamese pair. The server builds the saved translation map from those pairs, avoiding a separate source-text list that can omit or mismatch recipe fields. This uses one provider call and avoids repeating English instructions in the response.
- Each request includes one complete representative recipe from `public/meal-plan.json`, paired with its bundled Vietnamese translations, its original serving count and a compact vocabulary of default ingredient names. Gemini uses this example for detail and naming consistency while the current form controls ingredients, cuisine, servings, restrictions and equipment. A single recipe example keeps input quota lower than sending the entire default week.
- Form data and the master prompt are sent to Gemini. Free-tier data handling differs from paid services; review Google's current terms and avoid unnecessary personal information. The UI shows a short disclosure before generation. AI suggestions are not allergy or food-safety certification; the server also checks known restricted ingredients using the app's existing ingredient-warning rules.

Cloudflare Workers, D1 and Workflows have their own free-tier limits, separately from Gemini's quota. The deployment scripts do not enable a paid plan.

## Runtime and authentication

`/api/ai-menu` requires Access sign-in and the existing family code, validates inputs, saves master-prompt preferences/drafts and starts a Cloudflare Workflow. `MenuWorkflow` claims the job once, calls Gemini, validates the entire plan and saves either a ready draft or a failure code. Neither writes the active family planner. Queued/running jobs older than 20 minutes are reported as timed out.

The server-only D1 `ai` namespace contains settings, jobs and per-day allowance records. All application routes to it require the family code. Data is not saved into the Git repository. Provider error messages and API keys are not returned to the browser. Failed jobs may retain a numeric HTTP status, an allowlisted provider status and a fixed provider/validation diagnostic category. Instruction-detail failures can also record the canonical slot ID and numeric step/character counts; diagnostics exclude recipe text, prompts and credentials.

An administrator may seed a synthetic job with the internal diagnostic flag to capture a key-redacted provider message in the separate D1 `diagnostics` namespace. The generation API ignores that flag in browser requests. Remove the diagnostic record after troubleshooting; ordinary family jobs do not capture provider text.

The Interactions response format supplies the JSON schema directly. Only completed model-output text is read; thought steps and incomplete results are not accepted as recipes. The provider schema uses one reusable recipe shape in an array whose length equals the requested slot count. This avoids expanding the whole recipe schema into a separate property for every slot. Required English/Vietnamese pairs constrain missing-language errors; the server assigns canonical IDs, days and meal types from the ordered request slots. Earlier keyed bilingual results remain compatible. A previous schema with a required object property for every slot exceeded decoder constraints; plain JSON mode also allowed occasional missing bilingual fields. Validation enforces the exact requested meal count and slots, at most 30 ingredients, 10 preparation steps and 15 cooking steps per meal, complete bilingual text and quantity preservation. Invalid output never becomes an active or ready plan.

The translation map uses a protected dictionary during validation, then becomes a plain object through object spread before the Workflow step returns. Cloudflare's durable step serializer rejects null-prototype dictionaries. Object spread keeps keys such as `__proto__` as ordinary own properties without invoking a prototype setter.

Generated recipes also have a basic completeness floor: a separate side needs ingredient coverage, common bread/rice sides must appear in the ingredient list, and heated recipes need at least three actionable steps with 120 characters of cooking guidance. Ingredient amounts appearing in instructions must use scalable bracket tokens. Legitimate simple cold dishes with no side remain supported. These checks do not certify culinary completeness, allergy safety or nutritional adequacy; the draft remains editable and requires review.

Cloudflare Access email OTP replaces Netlify SSO on the new hostname. Only the configured owner email may sign in. The Worker verifies the Access JWT, and private planner/AI routes also require the family code. Workflows start through a server binding without forwarding login cookies. If the session expires, the sign-in link opens a new tab so the original form remains available. Legacy Netlify Functions remain for rollback only.

## Data compatibility

Schema v1 retains exactly ten weekday lunch/dinner slots. Schema v2 accepts 1–21 unique slots across all seven days and all three meal types, plus optional appliance metadata and an exact-source Vietnamese translation map. Legacy defaults and backups remain v1 and continue to work. The calendar, cooking picker, saved-food schedules, backup validation, shopping and preparation accept v2. Missing preparation compatibility profiles remain individual tasks rather than guessing shared preparation.

## Verification

`npm test` checks the wizard, preview/edit/apply workflow, existing-data preservation, 21-slot support, legacy backups, translation/quantity validation, selected appliances, authenticated endpoints, concurrent quota reservations, conditional draft writes, duplicate submissions, background failures and missing configuration. `npm run build` checks frontend and Worker TypeScript and builds static assets.

For the private Cloudflare deployment, run `python3 scripts/verify-cloudflare.py --url https://family-weekly-meal-planning.family-3adfa3459c6c.workers.dev --generate-menu` from `source`. This uses a temporary Access service identity, revokes it after testing and reports only sanitized results. It generates one synthetic ten-meal draft, consumes one daily allowance and leaves the active menu unchanged. A configured secret or successful build alone does not prove generation works.

The legacy `scripts/ai-live-smoke.mjs` remains disabled by default. Its Netlify-only **AI_RUN_LIVE_SMOKE=true** flag enables a synthetic one-meal provider check during an old-platform diagnostic build. Do not enable it for ordinary deployments; use the Cloudflare verification command above for the current production runtime.
